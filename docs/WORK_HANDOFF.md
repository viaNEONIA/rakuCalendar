## 1. 目的と優先順位
スマートフォンで1日の予定を素早く入力し、縦方向の時間軸上で直接移動・時間変更できる軽量PWAを作る。重要度は (1) 日表示の操作性、(2) 予定の永続保存、(3) 重複表示、(4) 現在時刻と次の予定、(5) バックアップ・復元、(6) ICS出力。

初期版は**日表示のみ**。過去のUIラフに登場した週・月切替は将来候補であり、初期版には含めない。クラウド同期、ユーザーアカウント、外部カレンダーAPIとの双方向同期も対象外。

## 2. 技術方針
- PWA: manifest、service worker、オフライン起動を備える。
- TypeScript + React + Viteを推奨（既存コードがあれば既存構成を優先）。
- IndexedDBに予定と設定を保存。スキーマ更新を考慮。
- モバイルファースト。タッチ対象は原則44〜48 CSS px以上。Android Chromiumを重点検証、iOS Safariも可能な範囲で検証。
- ローカル時刻とタイムゾーンを正しく扱い、保存・出力時の日時ずれを防ぐ。
- 依存ライブラリは最小限。パフォーマンス、アクセシビリティ、保守性を重視。

## 3. 予定データモデル
予定ID（UUID）、予定内容（必須）、行先（入力項目、必須扱いはUIで確認）、開始日時（必須）、終了日時（必須）、メモ（任意）、表示色（任意）、作成日時、更新日時。
- 新規作成の初期日付は作成当日、開始時刻は作成時点を選択刻みに丸めた値とする。終了時刻は開始後30分を初期案とする（実装上の仮決定）。
- 終了日時は開始日時より後でなければならない。日付をまたぐ予定はデータモデル上は扱えるようにし、日表示では当日部分をクリップする。
- 予定の時間重複は禁止しない。

## 4. 日表示UI
- 上部: 日付、前日/翌日、日付選択、設定への導線。
- 上部固定: 次に開始する予定（タイトル、開始時刻、残り時間）。タップでその位置へスクロール。同時刻開始が複数なら件数表示。予定なしの場合も適切に表示。
- 本体: 縦軸時間、予定カード、現在時刻の赤い水平ラインと時刻ラベル。現在時刻は1分ごとに更新し、当日以外は非表示。
- 起動時は現在時刻の約30分前が見える位置へスクロール。現在時刻へ戻るボタンを配置。
- 右下の「＋」で新規登録。時間軸の空白タップではその時刻を初期値にする。
- 時間軸の表示刻みとドラッグのスナップ刻みを分離する。10/20/30分から選択できる設定を用意。
- 予定の重複は横並びで表示。3件以上でカードが狭い場合、視認性を優先して件数表示・選択導線を用意。予定の重複数が変わっても予定時刻は変化させない。

## 5. 予定編集操作
- カードをタップ: 選択状態と編集ハンドルを表示。詳細編集も開ける。
- カードを長押しして上下ドラッグ: 所要時間を維持したまま開始/終了を移動。
- 上端ハンドル: 開始時刻変更。下端ハンドル: 終了時刻変更。
- ドラッグ中: 移動前の時間帯を薄い枠で表示、移動後の開始/終了時刻をプレビュー。
- 指を離した時点で確定・自動保存。操作後約5秒の「元に戻す」を表示。
- Undo/Redoを設ける。直前のドラッグ移動・延長・短縮が対象。履歴の保持範囲と再起動後の扱いは実装で明記。
- スクロールとドラッグが競合しないよう、長押し判定、タッチキャンセル、画面端自動スクロールを検証。
- 予定追加・編集フォーム: 予定内容、行先、開始日時、終了日時、メモ（任意）、色。保存・キャンセル・削除（編集時）。

## 6. 設定画面
- 表示と操作: 時間刻み、表示開始/終了時刻、現在時刻ラインON/OFF、次の予定ON/OFF、重複表示。
- 予定の色・ラベル: 必要最小限の色設定。
- バックアップと復元: **設定画面からのみ遷移**。
- 外部カレンダー出力: ICS書き出し。
- アプリについて: バージョン、基本的な使い方。

## 7. バックアップと復元
### 保存
- 全予定、メモ、色、表示設定、通知設定をUTF-8 JSONファイルに出力。
- ファイル名例: `rakuCalendar-backup-YYYYMMDD-HHmm.json`。
- JSONルート: `format`, `schemaVersion`, `appVersion`, `exportedAt`, `timezone`, `events`, `settings`。
- `schemaVersion` は初期値1。アプリバージョンとは別管理。
- 共有シートや端末のファイル保存を利用可能にする。保存操作の開始だけで完了と断定しない。
- 最終バックアップ日時を設定画面に表示。保存完了の確認が取れないブラウザでは、最終バックアップ「作成」日時など正確な文言を使う。
### 復元
- JSON選択 → 形式・サイズ・スキーマ・必須フィールド・日時・IDの検証 → 件数/バックアップ日時/設定内容のプレビュー → 復元方式選択 → 確認 → 実行 → 結果表示。
- 方式A（初期値）: 既存予定を残して追加・統合。ID一致で内容が同じなら重複登録しない。異なる場合は競合を明示して確認。
- 方式B: 全件置き換え。実行前に現在データの退避/エクスポートを促す。
- 復元はIndexedDBの単一トランザクション等で原子的に行い、失敗時は既存データを保持。復元直前の状態に戻す手段を設ける。ただしブラウザ保存領域の削除に耐えるものではない。
- 古いschemaVersionは明示的なマイグレーションで受け入れる。未対応の新しいschemaVersionは書き換えずに拒否。
- 不正なJSONや異常なデータ量に対するガードを設ける。読み込んだ文字列をHTMLとして実行しない。
### バックアップ忘れ防止
- オフ/7日/14日/30日。初期値は14日。
- 最終バックアップからの経過に応じ、アプリ起動時にアプリ内で注意表示。OSプッシュ通知は初期版で必須にしない。
- 自動バックアップを行うのではなく、手動保存を促す機能とする。

## 8. 外部カレンダー出力
- iCalendar `.ics` (RFC 5545) を生成。VEVENTにUID、DTSTAMP、DTSTART、DTEND、SUMMARY、LOCATION、DESCRIPTIONを出力。
- 日本語、改行、カンマ、セミコロン、バックスラッシュを適切にエスケープ。CRLFと行折り返し規則に配慮。
- 1件/指定日/全件の出力範囲を検討し、初期版は最低でも指定日の全件を出力。
- Google Calendar、Outlook、Apple Calendar等への**インポート用ファイル**として提供。各アプリへの直接登録や双方向同期が保証されると表示しない。
- JSONバックアップとICS出力の役割を明確に分ける。

## 10. 受入テスト
- 新規作成時に当日・現在時刻に基づく初期値が入る。
- 10/20/30分の設定とドラッグ時の時刻変更が正しい。
- 2件/3件以上の重複が表示され、カードを個別に選択できる。
- 予定移動時に長さが維持され、上下端操作でのみ長さが変わる。
- スクロール時の誤ドラッグ、短いカードのタップ、日付境界、画面端の移動を検証。
- 現在時刻ラインが更新され、過去日/未来日には表示されない。
- 次の予定の算出が現在進行中/同時刻複数/予定なしでも正しい。
- ページ再読み込み、オフライン再起動後に予定と設定が保持される。
- JSON出力→新規環境へ復元で予定・メモ・色・設定が一致する。
- 同一バックアップの再統合で重複増殖しない。壊れたJSONや未対応schemaVersionは安全に拒否。
- 復元失敗時に既存データが維持される。
- ICSを一般的なカレンダーアプリにインポートでき、日時・タイトル・行先・メモが保持される。
- モバイル幅360/390/412px程度、縦横画面、Android Chromiumを重点確認。
